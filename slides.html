ConceptCore Idea
How React avoids full DOM repaints

Virtual DOM &
Reconciliation

React keeps a lightweight JavaScript copy of the DOM. When state changes, it builds a new virtual tree, diffs it against the old one, and only touches the real DOM nodes that actually changed.

01
Virtual DOMA plain JS object tree representing your UI — cheap to create, cheap to compare.
02
DiffingReact compares old and new virtual trees to find the minimum set of real DOM changes needed.
03
FiberReact's internal work unit. Each component is a fiber node; the fiber tree is what gets diffed.
04
KeysHints to the reconciler for tracking list items. Wrong keys = wrong diffing = subtle bugs.

WalkthroughStep by Step
What happens on every state change

The
Render Cycle

01
TriggerA setState call, prop change, or context update schedules a re-render for the affected component.
02
Render PhaseReact calls your component function and gets a new JSX tree. Pure — no DOM side-effects happen here.
03
ReconciliationReact diffs the new fiber tree against the previous one and marks which nodes need to change.
04
Commit PhaseReact flushes all marked changes to the real DOM in one synchronous pass, then fires refs and effects.

Part 02Re-render Control
The first lever you should pull

Re-render
Control

Most performance bugs aren't slow code — they're too many renders of code that was already fast enough.

devweekends.com
Dev{Weekends}
ConceptCore Idea
Know the enemy before you fight it

What Triggers
Re-renders

A component re-renders when its state changes, its parent re-renders, or a context it consumes updates. Knowing each trigger tells you exactly which tool to apply.

01
State changeCalling a useState or useReducer setter always schedules a re-render for that component.
02
Parent re-renderBy default, every child re-renders when its parent does — even if no props changed.
03
Context updateAny component consuming a context re-renders whenever the context value reference changes.
04
Key changeChanging a component's key prop unmounts and remounts it entirely — a full state reset.

ConceptMemoization
Skipping unnecessary child renders

React
.memo

React.memo wraps a component and skips re-rendering if props haven't changed (shallow compare). It's the first tool to reach for when a child re-renders too often because its parent does.

01
Shallow comparePrimitives compared by value. Objects and arrays must be stable references to be considered equal.
02
Custom comparatorPass a second argument (prevProps, nextProps) => boolean for fine-grained control.
03
When to useExpensive components whose props rarely change — charts, tables, heavy list rows.
04
When NOT to useComponents that almost always re-render — the comparison itself has a measurable cost.
devweekends.com

ConceptHooks
Stable values and stable references

useMemo &
useCallback

useMemo caches a computed value. useCallback caches a function reference. Both return the same reference until their dependency array changes — preventing unnecessary re-renders downstream.

01
useMemoCaches expensive calculations: useMemo(() => heavyFn(data), [data]).
02
useCallbackStabilises function references passed as props to React.memo children.
03
Dependency arrayMust list every reactive value the hook reads. Lint with eslint-plugin-react-hooks.
04
The key ruleOnly worth it when the stable reference actually prevents downstream work — measure first.

Watch OutCommon Mistakes
Where developers go wrong

Memoization
Traps

!
Memoising everythingReact.memo and useMemo have overhead. Adding them blindly makes code slower, not faster.
!
Unstable object depsInline objects/arrays in a dep array break memoisation every render — { id } !== { id }.
!
Missing dependenciesStale closures from an incomplete dep array produce subtle bugs that are very hard to track down.
!
Wrong root causeMemoising a component that re-renders because of context won't help — fix the context shape instead.

ConceptCode Splitting
Ship only what the user needs right now

React.lazy +
Suspense

React.lazy() imports a component only when it's rendered. Wrapped in Suspense, React shows a fallback while the JS chunk loads — no manual loading state required.

01
React.lazyDynamic import() under the hood — each lazy component becomes its own JS bundle chunk.
02
SuspenseWraps lazy components; renders a fallback (spinner, skeleton) while the chunk is fetching.
03
Route-level firstSplit at routes first — biggest gains, least complexity. Go deeper only if routes aren't enough.
04
Nested SuspenseWrap sections independently so one slow chunk doesn't block loading the rest of the page.

ConceptAsync Patterns
Keeping the UI responsive during heavy work

Async
Rendering

01
useTransitionMarks a setState call as non-urgent. startTransition keeps inputs snappy; isPending drives a loading indicator.
02
useDeferredValueLets a derived value "lag behind" the urgent state — great for search/filter without wrapping setters.
03
Lazy image loadingAdd loading="lazy" to <img> tags — browsers defer off-screen image fetches natively, for free.
04
Intersection ObserverFires when an element enters the viewport — use for custom lazy loads, infinite scroll, and animations.

Part 04List Virtualization
Render 20 rows at a time, not 20,000

List
Virtualization

Long lists destroy performance because the DOM has to hold every node. Virtualization keeps only the visible rows alive.

devweekends.com
Dev{Weekends}
ConceptLibrary
Only visible rows live in the DOM

react
-window

react-window renders only the rows visible in the viewport. Every other row is a calculated offset — no DOM node, no memory, no render cost. Works for lists and grids.

01
FixedSizeListAll rows the same height. Simplest API — start here for uniform data like product or user lists.
02
VariableSizeListEach row reports its own height via a getItemSize function — more flexible for mixed content.
03
FixedSizeGrid2D virtualization for tables and image grids — rows and columns are both windowed.
04
overscanCountRenders a few extra rows above and below the viewport to hide scroll jank on fast scrolls.

ConceptEvent Control
Limit how often expensive work fires

Throttle &
Debounce

Both limit how often a function fires. Debounce waits until a burst stops. Throttle fires at most once per interval. The wrong choice makes UIs feel laggy or unresponsive.

01
DebounceDelays execution until N ms after the last call. Use for search inputs and form validation.
02
ThrottleGuarantees at most one call per interval. Use for scroll, resize, and mouse-move handlers.
03
300–500 ms sweet spotSearch debounce: 300 ms feels instant. API call debounce: 500 ms prevents over-fetching.
04
CleanupAlways clear timeouts in the useEffect cleanup function to avoid stale calls after unmount.

ConceptDOM & Threads
Keep the DOM lean and the main thread free

Fragments &
Web Workers

01
React.Fragment / <>Groups children without adding a wrapper DOM node — keeps markup clean and avoids layout side-effects.
02
Keyed fragmentsUse <Fragment key={id}> when mapping — you cannot put a key on the shorthand <> syntax.
03
Web WorkersMove heavy computation off the main thread. React renders on the main thread — workers run in parallel.
04
comlink / workerizeLibraries that wrap workers with a clean async API — call worker functions like normal async functions.

Watch OutAnti-Patterns
Where experienced developers still go wrong

Performance
Anti-Patterns

!
Inline functions in JSX<Button onClick={() => ...}> creates a new function every render, silently breaking React.memo on the child.
!
Context as a global storeOne context update re-renders every consumer — split contexts by update frequency or use Zustand/Jotai.
!
Syncing state from propsuseEffect(() => setState(prop), [prop]) causes double-renders. Compute in render or useMemo instead.
!
Skipping the profilerOptimising by instinct is guesswork that often makes things worse. Always measure before you fix.
